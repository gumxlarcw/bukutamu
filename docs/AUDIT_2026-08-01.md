# Bukutamu — Full-System Health Report

**Date:** 2026-08-01
**Scope:** 8 subsystem sweeps — backend-api, kiosk-flow, admin-panel, whatsapp,
status-gates, security, data-integrity, ops-deploy — plus infrastructure
(Apache vhosts, Cloudflare Tunnel, PM2, cron, backups, MariaDB).
**Branch audited:** `main` @ `eed8338`
**Report mode:** Read-only audit — findings only, no code changes applied.
No writes, no service restarts, no builds. `bukutamu-wa` was never restarted.

**Method:** each subsystem was swept independently, then every finding was
handed to a separate adversarial verifier instructed to *refute* it and to
default to REFUTED when the evidence could not be reproduced. 52 findings
survived; 4 were refuted and are listed as such in the Executive Summary so
they are not re-raised later. Findings still marked PLAUSIBLE are stated as
risk, not as fact.

**Result:** 52 confirmed (7 high · 25 medium · 20 low) + 3 plausible.
Predecessor report: [`AUDIT_2026-05-16.md`](AUDIT_2026-05-16.md).

## Executive summary

The application logic is in better shape than the perimeter. All three documented SKD finalization gates hold (plus a fourth mirror in `Dtsen.php`), the `count_all_results()` mass-update footgun is correctly hoisted at all six call sites, there is zero schema-vs-code drift, zero SQL injection, zero dead routes, and the DELETE cascade is complete with zero orphans in the DB.

The serious problems are all **exposure and infrastructure**:

1. Two unauthenticated endpoints hand the entire guest roster and **235 face-biometric templates** to the public internet.
2. Because `proxy_ips` is empty behind the Cloudflare Tunnel, **every client is `::1`** — five HTTP requests from anywhere lock all 8 admin accounts out indefinitely.
3. The weekly 29 GB Google Drive backup **includes the live WhatsApp session credentials** plus an `--all-databases` dump.

Plus one live data-quality defect: the published "Rata-rata Durasi Layanan" KPI is inflated ~3.4×.

Two auditor claims were **refuted** by the verifier and are excluded: the "false print-failed toast" (no `<Toaster/>` is mounted anywhere in the app, so no toast can render), the "`Lainnya Online` visits can never be closed" (the Proses→form→Simpan path closes them), the `PUT /api/visits/:id/service` duplicate-ticket story (all cited duplicates predate commit `ce9edc6`), and the `killBrowserSync()` critique (logs show it targets the post-launch in-process orphan, which it reaps correctly).

## CONFIRMED findings — ranked by real-world risk

### 1. Public unauthenticated dump of the guest roster + 235 face-biometric templates — **CRITICAL in practice**
**Areas:** backend-api, security · **File:** `/var/www/html/bukutamu/backend/application/modules/api/controllers/Kiosk.php:8-33` (`face_data`) and `:35-50` (`guest_list`) · routes `routes.php:79-80`

One GET returns **635,646 bytes** of JSON: `id_user`, `nama` and the 128-float face template for all 235 enrolled visitors (243 guests total, 235 with descriptors). A second returns name + `nama_instansi` for all 243. Sole guard is `require_rate_limit(..., 30)` — irrelevant, because one request is the whole table, and per finding #2 that limiter is a single global bucket anyway.

The in-code comment at `Kiosk.php:13-16` claims an Apache IP allowlist is the perimeter. **It does not exist** — both `/etc/apache2/sites-enabled/bukutamu-60.conf` and `bukutamu-ssl.conf` were read end to end; neither contains any `Require ip` or `<Location /api/kiosk>` block. Proven live through the real edge (`curl -H 'Host: bukutamu.bpsmalut.com' http://localhost:60/api/kiosk/face-data` → 200, 635,646 bytes). Crawlers are already walking this vhost — the `::1` lines in `bukutamu60_access.log` carry `Googlebot/2.1` and `OAI-SearchBot/1.0` user-agents.

Two corrections worth carrying forward: (a) the descriptors are **not** a replay credential — matching runs client-side, and `Kiosk::visit` accepts a bare `id_user` with no face proof anyway; the harm is the disclosure itself (irrevocable biometrics of 235 named people from a government system, UU PDP). (b) **Do not fix this with an Apache IP allowlist** — see finding #2; `Require ip 10.x` written today blocks the kiosks and admits the internet.

**Fix:** mint a long-TTL `kiosk-device` token via the existing `Api_base::mint_kiosk_token` (`Api_base.php:523`) and `require_kiosk_token` at the top of both methods. Add a `LIMIT` so no single request is ever a full dump. Longer term, move matching server-side so descriptors never leave the box.

### 2. Every client IP collapses to `::1` — global admin lockout with 5 requests — **HIGH**
**Areas:** backend-api, security · **File:** `/var/www/html/bukutamu/backend/application/config/config.php:531` (`$config['proxy_ips'] = '';`)

`/etc/cloudflared/config.yml` routes `bukutamu.bpsmalut.com → http://localhost:60`; `mod_remoteip` is **not** enabled (`ls /etc/apache2/mods-enabled | grep remoteip` → empty) and no `RemoteIPHeader` exists anywhere in `/etc/apache2`. With `proxy_ips` empty, `Input::ip_address()` never consults XFF and returns `REMOTE_ADDR` = loopback for all public traffic. Confirmed in production data: `tamdes_login_attempts` → `::1`=410, `127.0.0.1`=3, nothing else; `tamdes_audit_log` → `::1`=1109. All 8 `POST /api/auth/login` requests across every rotated log came from `::1`.

Three consequences:
- **Login lockout is global and self-renewing.** `Auth.php:53-61` counts failures by IP with **no `username` predicate**, and returns 429 at `Auth.php:61` *before* `password_verify`. Five bad logins lock `admin, nayla, irma, nita, halima, fenty, wisnu, mutia` for 15 min. Worse: `Auth.php:62` writes *another* `success=0` row on the already-rejected path, so every honest staff retry slides the window forward. An attacker needs 5 requests once; the admins then keep themselves locked out.
- **`require_rate_limit` is one global 30/min bucket** (`Api_base.php:598`) — an outsider can 429 the physical lobby kiosks by hammering `/api/kiosk/register`.
- **Zero source attribution** in 1109 audit rows.

**Fix — order matters.** (1) One-line, do first: make the lockout per-account (`->where('username', $username)` at `Auth.php:53-61`) and stop logging a failure at `Auth.php:62` when already locked. That removes the DoS on its own. (2) Then fix the IP: `a2enmod remoteip` + `RemoteIPHeader CF-Connecting-IP` + `RemoteIPTrustedProxy 127.0.0.1 ::1` in **both** vhosts, leaving `proxy_ips` empty. **Do not** set `proxy_ips='127.0.0.1,::1'` — Cloudflare *appends* to a client-supplied `X-Forwarded-For` and CI3 takes the first element, which would hand attackers full control of `ip_address()` and let them forge source IPs into the audit log. That is strictly worse than today.

### 4. Published "Rata-rata Durasi Layanan" KPI is ~3.4× inflated — **HIGH (wrong data, live, on a reported metric)**
**Areas:** status-gates, data-integrity · **Writers:** `Visits.php:291-292`, `Consultations.php:224-225` and `:405`, `Dtsen.php:210` and `:286`, `Evaluations.php:243-244` · **Consumers:** `Queue_stats.php:17-21`, `:59`, `:69`, `Dashboard.php:57` · **UI:** `QueueStatsPage.tsx:351`, `DashboardPage.tsx:86`

Every finalization path stamps `durasi_detik = max(0, now − date_visit)` with no upper bound. Measured on production: 2026 `AVG` = **46,877 s (13.0 h / 781 min)**; the same query with `durasi_detik < 86400` = **13,644 s**. 20-21 of 219 durationed rows (9%) exceed one day. Worst row: `id_kunjungan 990679`, `date_visit 2026-07-17 10:31:36`, `selesai_timestamp 2026-07-31 16:50:02`, `durasi_detik 1,232,306` (342 h), `["Perpustakaan"]` — its audit trail shows no close event at all, i.e. the poison arrived through the `Evaluations` POST path, which writes no audit row.

This is a KPI a statistics office reports. Closing the 11 currently-parked Rekomendasi visits (finding #17) through the normal UI would add eleven ~18-day rows. Note the compounding path: `Evaluations.php:202` derives `$is_first_submit` from `status === 'menunggu_evaluasi'`, so any downgrade back into that state **re-stamps** a stale duration on the next eval submit.

Also change `Evaluations.php:202` to key off `selesai_timestamp === null` instead of status.

### 5. Account deactivation is broken on both ends — **HIGH**
**Areas:** admin-panel, security · **Files:** `frontend/src/pages/admin/UserManagementPage.tsx:116,121` + `frontend/src/api/users.ts:11`; `backend/.../Api_base.php:39-55`, `:119`; `libraries/JWT_Helper.php:7`

Two independent defects that compose into "you cannot actually revoke an admin":

**(a) FE numeric-string coercion (CONFIRMED).** CI3 mysqli returns `active` as the string `"0"`. `UserManagementPage.tsx:116` is `{!u.active && <span>Nonaktif</span>}` — `!"0"` is `false`, so the badge never shows and the superadmin thinks the deactivation failed. Line 121 is `active: !!u.active` — `!!"0"` is `true`, so the **next edit of that user (rename, phone, role, password reset) silently PUTs `active: true`** and `Users.php:99` writes 1 back, restoring login. `users.ts:11` declares `active: number`, so `tsc` cannot catch it. `active` is the real login gate (`Auth.php:68-71`). All 8 rows are currently `active=1`, so this is latent — it breaks the first time deactivation is used.

**(b) JWT has no revocation (CONFIRMED).** `require_auth()` decodes the cookie and never re-reads `admin_users` — no `active` check, and `require_role()` authorises off the **JWT's** role claim (`Api_base.php:119`). Grep confirms `active` is consulted only at login. TTL is 4 h (`JWT_Helper.php:7`), no refresh. So a deactivated, deleted or demoted account keeps every protected endpoint for up to 4 hours. `/api/auth/check` *does* return the fresh DB role, so the UI changes — a UI-only illusion of revocation.

**Fix:** (a) type `active` as `number | string` in `users.ts:11` and derive `const isActive = Number(u.active) === 1` once per row (mirrors the existing `GuestListPage.tsx:73` precedent). (b) In `require_auth()`, after decode, re-read `admin_users` by username, 401 if missing or `active <> 1`, and overwrite `current_user->role` from the DB row. **Exempt the `.env` fallback identity** (`Auth.php:86-99` issues tokens with `id=0` and no `admin_users` row) or that login path starts 401ing.

### 7. Session cookie issued without `Secure`, and plain HTTP is served — **MEDIUM**
**Area:** security · **File:** `backend/.../Auth.php:120-126` and `:163-169`

`'secure' => (!empty($_SERVER['HTTPS']) && ...)` — but the public path terminates TLS at Cloudflare and reaches Apache over plain HTTP, and nothing sets `HTTPS=on` (no `SetEnvIf`/`RequestHeader` in either bukutamu vhost, no `env[]` in the FPM pool). So the 4-hour admin `jwt_token` is issued **without `Secure`**. The precondition is satisfied: `curl -I http://bukutamu.bpsmalut.com/api/auth/check` returns a live **405 API response, not a 301** — Cloudflare "Always Use HTTPS" is off and there is no HSTS header on either scheme. Note CI3's own cookies *are* `Secure` (`config.php:406` derives it from `base_url`, verified live: `set-cookie: ci_session=...; secure; HttpOnly`) — so this is an internal inconsistency, not a deployment ambiguity.

**Fix:** `'secure' => (bool) $this->config->item('cookie_secure')` at both sites; enable Cloudflare "Always Use HTTPS" + HSTS. Don't derive it from `X-Forwarded-Proto` — client-influenced headers should not decide a cookie flag.

- **Physical kiosk hardware** — camera, face-recognition accuracy in real lighting, the actual walk-up experience. Face tuning constants were verified as *code* (`WARMUP_MS=600`, `SAMPLE_TARGET=5`, threshold 0.55 / margin 0.08, single-sourced and mirrored at `Kiosk.php:644`), not as behaviour.
- **USB thermal printer / `print/server.js` end-to-end.** The JSON contract was verified by reading both sides; nothing was printed. `print/` does not run on this server.
- **Real visitor traffic.** No smoke script under `scripts/smoke/` was run — they write to the production DB.
- **No live WhatsApp send, and no PM2 restart of `bukutamu-wa`.** The `pair_phone` (#11), `cancelPairingCode` and outbox-fail paths were verified by code + DB + log reading only. The connector has been idle since 2026-07-18, so the inbound path was not exercised live.
- **The login-flood DoS (#2) was not executed** — it would have caused a real staff lockout. The code path is unambiguous and every leg was reproduced statically and against `tamdes_login_attempts`.
- **The biometric dataset was not exfiltrated.** Reachability was proven with a `HEAD` (405 before the rate-limit INSERT) and a single 200 with byte count; the payload was not retained.
- **No cached-response artifact** for the `Guests::photo` `Cache-Control: public` issue — Cloudflare's standard cache level does not cache extensionless dynamic paths on origin headers alone, so the cross-user leak remains theoretical.
- **Cloudflare dashboard settings** were inferred from response behaviour (no 301 on http, no HSTS header), not read from the CF console.
- **The reason MariaDB's binlog purge is not firing** was not determined — config is applied, no replica is pinning, `log_error` is empty.
- **No automated test suite exists in this repo** (no PHPUnit, no Vitest, no Playwright). Everything above is static reading plus read-only DB/log/process inspection. Any fix below needs manual verification against the cross-component checklist in `.claude/rules/testing.md`.
